## 二、依赖关系（关键）

```
文件查看器 ──┐
             ├──► 云盘管理 PR4（下载走引擎、预览走查看器）
下载管理器 ──┘
```
- **文件查看器**与**下载管理器**互不依赖，是两条可并行的独立轨道。
- 二者都是**云盘的基石**：云盘 PR4 才需要它们；云盘 PR1–PR3（Provider+适配器+转存）不硬依赖，可提前起步。
- 唯一的共享接线点是 `main.go`/`main_server.go`：查看器包一层 `MediaHandler`（Range 端点），下载器/云盘各加一行 `RegisterEvent`。改同一对文件 → **宜串行、避免反复重生成 bindings 冲突**。

## 三、推荐顺序：查看器 → 下载器 → 云盘

**为什么查看器排第一**
- 完全自包含、耦合面最小，做完即独立交付一个用户直接要的能力（看图/编辑/预览）。
- 它是云盘 PR4 的前置之一，早做早解锁。
- 唯二动到 `Assets.Handler` 包装的方案就是它（下载器不碰），先做把这个易冲突点一次性解决。
- 只有它新增前端 npm 依赖（codemirror/xlsx），先把"构建分包 >500kB"这个风险提前踩平。

**为什么下载器排第二**
- 引擎仍是自包含，且此时"Range/ServeContent + 两 main 接线"模式已由查看器验证过，下载器的分块 Range 续传可复用同一套认知。
- PR1 是纯 Go + 单测的重活、前端风险低，适合紧随其后落地。
- 做完它，云盘的"下载"就能直接调引擎而非各写一套。

**为什么云盘排最后**
- PR4（打通）必须等查看器与下载引擎就绪；放最后可让云盘下载/预览天然复用前两者，不重复造轮子。
- 云盘是三者里外部风险最高的（国内两家现网接口脆弱、随时失效），把不确定放后面，先用已验证的地基承接。
- 但云盘 **PR1 核心（Provider+Google+store+cred+浏览管理）可在下载器 PR1 落地后并行起步**，无需等满。

## 五、可并行与必须串行

- **可并行**：M1–M2（查看器线）与 M3–M5（下载器线）互不依赖，两条轨可同人交替或并行；M6 云盘核心可在 M3 之后提前起步。
- **必须串行/一次一份**：`main.go`/`main_server.go` 接线、`config.go` Tools 注册、`tasks.go` events、以及每份计划末尾的 `wails3 generate bindings` —— 这些改的是同一批共享文件，**一份计划的绑定重生成/提交完成后，再开下一份**，否则 bindings 互相覆盖、diff 难查。
- **硬门槛**：M9 只能在 M2 且 M3（实际还需 M4 的落地页）都完成后做。

## 六、一句话结论

先 **查看器**（自包含、解锁预览、踩平前端依赖），再 **下载器**（引擎复用查看器的 Range 认知、解锁下载），最后 **云盘**（PR1 可提前并行，PR4 承接前两者）；三份共享文件接线与绑定重生成严格串行，一次只推进一份到可提交状态。
