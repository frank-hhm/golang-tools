## 一、List 翻页（`objectstore.go`）

- `osListResp` 补 `IsTruncated` / `NextMarker`；`List` 改为 marker 游标循环，每页 `max-keys=1000`，上限 `osListMaxPages=50`（5 万条），拿不到游标或与上一页游标相同即停——**不冒死循环风险**。
- 单页分类逻辑抽出 `classifyListPage`（行为与 PR-A 一致：CommonPrefixes 归目录、Contents 归文件、跳过目录占位对象）；新增 `lastListKey` 作为服务端未回 `NextMarker` 时的游标回落（取本页字典序最后一个 key，**含不展示的目录占位对象**，它仍是合法游标）。
- `encoding-type=utf-8` 时 `NextMarker` 也是编码态，必须 `unescKey` 还原后再当下一页参数传。

## 二、大文件分块上传（`objectstore.go`）

- 新增包级可调参数：`osPartSize`（8 MiB）、`osMultipartThreshold`（8 MiB）、`osMaxParts`（10000，三家共同的单对象片数上限）；测试里 `shrinkParts` 临时调小以低成本触发。
- `Upload` 分流：已知大小且 `size <= 阈值`（含 size=0 的空文件）走整段单 PUT；`size > 阈值` 或大小未知（`size < 0`）走 `uploadMultipart`——**修掉 PR-A「整段缓冲」的内存风险**：现在内存一次只驻留一片。
- `uploadMultipart` 走原生四步：`POST /<key>?uploads` 取 UploadId → 逐片 `PUT /<key>?partNumber=N&uploadId=…` 收服务端 ETag（原样带引号回传）→ `POST /<key>?uploadId=…` 提交 `<CompleteMultipartUpload>` 清单 → 失败或读流出错**立即 `DELETE /<key>?uploadId=…` Abort**（未 Abort 的分片会持续占容量计费）。
- 边界处理：超大对象按 `osMaxParts` 摊薄片大小；空文件退回单 PUT 零字节（Complete 空清单会被服务端拒）；Complete 回 200 但体内是 `<Error>` 一样判失败（沿用 PR-A 对 copy 的同一手法）。
  > **【PR-C 后续修订】** 断点续传已在 PR-C 落地（`uploads.json` 会话 + ListParts 核对），因此「分片写失败立即 Abort」只适用于**源不是本地文件**的情形；源是本地文件时改为保留会话不 Abort。详见 `变更-云盘对象存储PR-C签名严格校验与续传-20261104.md` 第三节。
- 进度上报不受影响：上层 `transfer.go` 用 tracker 包住 reader，分片照样从该 reader 读。
- `Provider` 接口与 `services/app` 绑定**零改动**，因此前端与绑定文件本次未重新生成。

## 三、Quota 覆盖三家（`objectstore.go`）

- 去掉 `kind != KindAliyunOSS` 的短路：三家统一发 `GET /?stat`。OSS 与 COS 都有 GetBucketStat（回 `<Storage>`）；通用 S3/MinIO 多数未实现，请求失败或解析不出即回 `{0,0}` 且**不报错**（前端 Total=0 就不展示总量）。

## 四、修掉的签名隐患：canonical query 双重转义（`signer.go`）

- `signQuery` 原先把 URL 里的原始（已编码）值直接送进 canonical 计算，而 `sortedKV.encode` 会再转义一次 —— 结果是 `marker=docs%2Ff1000.txt` 被签成 `docs%252Ff1000.txt`。真实服务端解码一次后重新编码得到单层，签名必然 `SignatureDoesNotMatch`；**只要目录层级里有 `/`（即非根目录翻页）、prefix 含空格或中文就会踩**，httptest 假后端不重算签名所以完全看不出来。
- 修法：`signQuery` 对值做 `url.QueryUnescape` 还原成原始值，两家再各自按规范转义一次（SigV4 在 `sortedKV.encode` 里 URI-encode，OSS canonical resource 直接拼原值，与官方 SDK 口径一致）。顺带确认 `?uploads` 这类空值子资源在 OSS canonical 里写成 `uploads`（不带等号）、在 SigV4 里写成 `uploads=`，两者都由这条路径统一。
- 回归锁：`TestCanonicalQuerySingleEncode` 断言「解码→再编码」幂等，且空值子资源两种写法各按其规范。
  > **【PR-C 后续修订】** 同一函数族里又查出两处真机级签名缺陷：预签名 URL 的 canonical 正文哈希行应写字面量 `UNSIGNED-PAYLOAD`（原写空串 SHA256），且 `X-Amz-Credential` 里的 `/` 必须参与转义（原 `skipEncode` 特例跳过）。另外 `copyObject` 的 copy-source 未做 URL 编码也属同类隐患。见同一文档第一、二节。
