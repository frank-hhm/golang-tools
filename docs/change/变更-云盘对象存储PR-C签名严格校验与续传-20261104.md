## 一、①：假后端按规范另写一套签名重算（`objectstore_auth_test.go`，608 行）

前两次 PR 各漏了一处**真机必炸**的签名缺陷（PR-A 的正文哈希写成 `SHA256(MD5(body))`、PR-B 的 canonical query 双重转义），单测却一路全绿——因为 httptest 假后端只看请求形状、从不重算签名。本轮把这一层补上：

- `verifyAuth(r, body, akID, secret)` 四路分发：`Authorization: OSS ` / `Authorization: AWS4-HMAC-SHA256 ` / 预签名查询串 `X-Amz-Signature` / 预签名查询串 `Signature`+`OSSAccessKeyId`；不通过即回 **403 + XML Error**（带错误码 `SignatureDoesNotMatch` / `XAmzContentSHA256Mismatch` / `BadDigest` / `InvalidAccessKeyId` / `RequestTimeout` / `AccessDenied` …，并把 canonical 附在 Message 里方便定位）。
- **关键纪律**：该文件刻意**不调用** `signer.go` 的 `signQuery` / `ossCanonicalResource` / `sortedKV` / `uriEscape` / `hmacHash` / `sha256Hex`——复用生产代码的规范化助手等于自己证自己，正是前两次漏检的原因。`fakeEncode`（RFC3986 逐字节、大写 %XX）、`fakeCanonicalQuery`（解码一次→各转义一次→按编码后 key/value 排序）、`fakeCanonicalHeaders`（要求含 host、要求声明列表本身已排序、值压空白）、`fakeOSSSubres`（按官方文档另抄 22 项）、`fakeOSSResource`、`fakeSigV4Key`（四级派生）全部另实现一遍。两边任何一处理解不一致，立刻变红。
- 顺带钉住的次要约定：`x-amz-content-sha256` 必须存在且与正文实际哈希一致；`x-amz-date` 必须与 credential scope 的日期同天；SignedHeaders 未排序/缺 host 视为非法；预签名的 `Expires` / `X-Amz-Expires` 过期即 `AccessDenied`。
- 假后端**没有关掉校验的后门**：原来的 `skipAuthCheck`/`noAuth` 已删除，任何请求都必须过签名重算。
- 3 组用例：`TestFakeBackendRejectsTamperedRequests`（5 个子测试：错签名 OSS / 错签名 SigV4 / 正文摘要不符 SigV4 / 正文摘要不符 OSS / 签 a.txt 却发 b.txt）、`TestPresignedURLVerifiesAgainstFake`（三家 presign 后真发 `http.Get` 取回字节一致；把 `Expires` 改一个数字必须 403）、`TestSignatureCoversNonASCIIQuery`（三家，前缀 `报告 v1+2` 的 List 必须过验签）。
- **变异测试**：把 `signQuery` 的 `url.QueryUnescape` 删掉（还原 PR-B 修复前的双重转义），`TestListPagination` 与 `TestSignatureCoversNonASCIIQuery` 立刻 FAIL（403 SignatureDoesNotMatch）→ 证明这套校验器真有牙。

## 二、本轮新发现的 5 处缺陷（3 处生产 + 2 处 mock 失真）

| # | 位置 | 缺陷 | 真机后果 |
|---|---|---|---|
| 1 | `signer.go` `s3Signer.presign` | canonical request 的正文哈希那一行写了「空串的 SHA256」 | 预签名 URL 永远 `SignatureDoesNotMatch`。规范（AWS SDK / MinIO / 阿里 S3 兼容文档）在查询串签名场景一律写字面量 `UNSIGNED-PAYLOAD`，已改为 `unsignedPayload` 常量 |
| 2 | `signer.go` `sortedKV.encode` | 原先对 `X-Amz-Credential` 跳过转义（`skipEncode` 特例） | 服务端按「解码后再转义一次」重算，`/` 必须写成 `%2F`；漏转义同样永远签名不匹配。已删特例，`rawQueryEscape` 降为单参 |
| 3 | `objectstore.go` `copyObject` | `x-oss-copy-source` / `x-amz-copy-source` 直接拼原始 key | 带空格/中文的源不是合法 header 值；且 key 里的 `+` 会被服务端解成空格 → `InvalidArgument` / `NoSuchKey`。已改为 `uriPathFromResource(o.resource(srcKey))`（URL 编码态） |
| 4 | `objectstore_test.go` `handle` | 对 `r.URL.Path` 又套了一次 `url.QueryUnescape` | mock 自己的双重解码，还把 `+` 当空格：同一个 key 存和取不是同一对象。真机不解这一遍。已改为直接用 `r.URL.Path`（Go 已按百分号解一次） |
| 5 | `objectstore_test.go` `list` | 不带 `delimiter` 时仍把以 `/` 结尾的项写成 `CommonPrefixes` | 真机在无 delimiter 时目录占位对象就是个**普通对象**，应进 `Contents`。这条失真会让新写的 `listAllKeys` 永远看不到占位对象，搬/删目录漏掉它们 |

3/4/5 都是**动手写 ②③ 的用例才暴露**的：#4、#5 属 mock 与真机不符（会掩盖真机问题），#3 是 PR-A 就潜伏的生产缺陷。

## 三、②：分块上传断点续传（`uploads.go` 新增 254 行 + `uploadMultipart` 重写）

- 新增 `uploads.json`（与 `accounts.json` 同目录，`appdirs.Data("clouddrive")`，写时 tmp+rename、`0600`）。每条会话只存**坐标**：账号 id、目标 key、云端 UploadId、片大小、源文件指纹（绝对路径 + 大小 + mtime 毫秒）、已确认分片（片号/ETag/大小）、创建与更新时间。**不落任何凭证**（`TestUploadSessionFileCarriesNoSecrets` 直接读文件断言不含 AK/SK）。
- 只有**源是本地文件**才建会话：`localSource(r)` 顺着 `countingReader.underlying()`（本轮给 `transfer.go` 加的透传）逐层剥出 `*os.File`。`services/app` 的 `CloudUpload` 传下来的正是 `tr.Wrap(ctx, f)`，不透传就永远拿不到文件、续传形同虚设。内存流 / 跨盘转存的远端流不具备「重启后内容可比对」的前提，**不走续传**。
- 续传前**必与云端核对**：`listUploadedParts` 发 `GET /<key>?uploadId=…`，用 `syncParts` 只保留**从第 1 片起连续**的那些片（中间断号就无法合成完整对象，后面的片一律当没传过、按同片号覆盖重传），回字节数作 `skip`；`discardBytes` 优先 `Seek`，不能 Seek 才 `CopyN`（读不满即判定「源文件已变化」并报错）。ListParts 回 `IsTruncated` 时**不猜**，直接拒绝续传、重头传。
- 会话复用条件（`matches`）：同 key + 同绝对路径 + 同大小 + 同 mtime + **同片大小**（片大小变了字节边界就对不齐）。任一条不符 → 当没有会话，重新 `POST ?uploads`。
- 失败处理分野：分片写失败时，源是本地文件 → **保留会话**（不 Abort，云端已传分片下次还要用）；源非文件 → 立刻 `DELETE ?uploadId=`（未 Abort 的残片持续占容量计费）。Complete 失败 / 片数超限 / 跳过字节失败 → 一律 Abort 并删会话；Complete 成功 → 删会话。每片成功即 `putUploadSession` 落盘，崩在两片之间只丢最后一片。
- TTL 24 小时：`loadUploadSessions` 把过期（或 UploadId/Key 为空的脏）记录剔出并回给调用方，`abortExpired` 用独立 30s 超时的 background ctx **尽力** Abort（失败不报，真正的兜底是 bucket 生命周期规则）。注意这是「该账号下次上传时顺带清理」，某账号此后再不上传，其过期记录会留在盘上（不影响正确性，只占几行 JSON）。
- 落盘读写失败不阻断上传（坏 JSON 当空表处理）；会话写失败只是「下次没法续传」。
- 已知小别扭（非缺陷）：续传时进度字节从跳过点起算，前端百分比起点不是 0。

## 四、③：目录整体改名/移动 = 批量 copy 前缀（`objectstore.go`）

- 列表公共部分抽成 `listBaseQuery` / `listPage` / `nextListMarker`（`List` 复用，行为不变），新增 `listAllKeys(prefix)`：**不带 delimiter** 全量列举前缀下每一个 key（含目录占位对象）。
- `copyPrefixTree(src, dst)`：**两遍式**——第一遍把每个对象按相同后缀 `copyObject` 到新前缀，全部成功后第二遍才逐个 `deleteKey` 删源。中途失败时旧目录仍完整可用（`TestDirRenameStopsBeforeDeletingSource` 钉住），故障撤掉后重跑同一操作会覆盖已搬的那几个并继续，**可幂等续跑**。拒绝「移动到自己之下」（`dst` 以 `src` 为前缀）与前缀为空（目录不存在/已为空）。
- `Rename` / `Move` 的 `isDirKey(id)` 分支改走 `copyPrefixTree`：以前只搬目录自身的空占位对象，子对象全留在原地。
- **顺带修掉同源缺陷**：`Delete` 对目录原先也只删占位对象，剩下的子对象会让目录在列表里**原地复活**。现改为按前缀 `listAllKeys` 逐个删（内部用 `deleteKey` 原语，`copyPrefixTree` 亦复用，避免递归绕路）。
- 如实标注两条限制：这一过程**非原子**（对象存储没有原生目录语义，中途失败会留下新旧两份，需重跑或手工清理）；单次服务端 copy 三家都有 **5 GiB** 上限，超限的大文件需要分块复制，**本次未实现**。

## 八、仍须真机确认（不可由 mock 裁断）

1. `X-Amz-Credential` 与 canonical query 的 `%2F`、预签名正文行 `UNSIGNED-PAYLOAD`：各家（OSS 的 S3 兼容层 / COS / MinIO / 真 S3）实现是否一致。校验器里那一行是唯一向生产约定看齐的写法，属**约定**而非规范强制。
2. copy-source 在 path-style 与虚拟主机式下分别该写 `/bucket/key` 还是 `/key`；带 `+`、空格、中文的源各家的解码口径。
3. ListParts 的分页参数名与 `IsTruncated`/`NextPartNumberMarker` 各家差异（本轮采取「截断就拒续传」的保守策略）；Abort 后容量是否真回收、残留分片多久计费。
4. 目录整体搬一个大目录的实际代价：`1 次全量列举 + N 次 copy + N 次 delete`，十万对象级目录不可用（需改用清单 + 并发/生命周期规则），以及 5 GiB 单次 copy 上限的大文件分块复制仍未实现。
5. `uploads.json` 的权限位与多进程并发写（当前 `uploadsMu` 只保证**进程内**串行）。
6. 时钟偏移、TLS、bucket policy、真实 `?stat` 字段（PR-B 遗留项）。
7. **续传会话暂无 UI**：`uploads.json` 只有后端读写，前端看不到「哪些文件处于待续传状态」、也不能手动丢弃某条会话（下次传同一文件会自动复用/自动丢弃）。需要时单开一期（导出方法 + 绑定重生成 + 列表）。
8. 腾讯微云（个人网盘逆向）**仍搁置**，需要时单开计划。
