## 一、签名层 `tools/clouddrive/signer.go`（新增，427 行，纯 stdlib）

- `type signer interface { sign(req *http.Request, resource string, payload []byte) error; presign(method, resource string, expiry time.Duration) (string, error) }`——两家各自从**正文原字节**里取自己需要的摘要（见 §八的缺陷修复）。
- `ossSigner`（阿里 OSS 原生 V1）：`Authorization: OSS <akid>:<base64(hmac-sha1)>`；stringToSign 依次为 VERB / Content-MD5 / Content-Type / Date / CanonicalizedOSSHeaders+CanonicalizedResource；有正文才给 `Content-MD5`；同时写 `Date` 与 `x-oss-date`；子资源白名单 `ossSubresources`（含 `stat`）参与 canonical query。
- `s3Signer`（AWS SigV4，**COS 与通用 S3 共用**）：`X-Amz-Content-Sha256` + `X-Amz-Date` + 四级派生密钥（`date/region/s3/aws4_request`），`Authorization: AWS4-HMAC-SHA256 Credential=…/, SignedHeaders=…, Signature=…`。时刻**只用 `x-amz-date` 表达**（不写标准 `Date` 头，与 AWS 官方实现一致）；参与签名的头为 host + content-type + 全部 `x-amz-*`。
- 寻址约定：签名用资源路径统一写成 `/<bucket>/<key>`（虚拟主机式与 path-style 同规则）；`uriPathFromResource` **保留目录 key 的尾斜杠**（否则 `Mkdir` 的 PUT 会打到 bucket 根）；`rawQueryEscape`/`uriEscape` 处理 `+`、`*`、`~` 与保留字符差异。
- presign：OSS 走 `OSSAccessKeyId/Expires/Signature`，SigV4 走 `X-Amz-Credential/Algorithm/Date/Expires/SignedHeaders/Signature`，默认 24h。

## 二、通用基座 `tools/clouddrive/objectstore.go`（新增，467 行）

- `objectStore{acctID, hc, bucket, host, region, kind, name, signer}` 实现 `Provider` 全部 11 个方法，三家共用一份实现；`newObjectStoreAcct(kind, name, acctID, Account, tokenBlob)` 按 kind 挂 signer（OSS→`ossSigner`；其余 region 空回落 `us-east-1`→`s3Signer`）。
- 语义映射（`Entry.ID` = 完整 object key）：`List` 用 `prefix+delimiter=/+encoding-type=utf-8+max-keys=1000`，`CommonPrefixes`→目录、`Contents`→文件（**跳过以 `/` 结尾的目录占位对象**，避免同一目录出现两行）；`Mkdir` PUT `<dir>/` 零字节；`Rename`/`Move` = 服务端 copy（`x-oss-copy-source` / `x-amz-copy-source`）+ `DELETE` 原 key；`Delete` DELETE；`ShareLink` presign GET 24h；`Open` GET 流（size 取 Content-Length）；`Upload` 整段单 PUT + Content-Type，再 HEAD 一次补 size/mtime/mime；`Test` `GET ?max-keys=1`；`Quota` 仅 OSS 走 `GET /?stat`，COS/S3 返回 `{0,0}`（失败也回零值不报错）。
- 错误透出：非 2xx 读 body 解析 XML `Code/Message`（`osErrMsg`），**copy 返回 200 但体内是 `<Error>` 也判失败**（COS 的坑）。
- 测试引流：包级 `var objectStoreScheme = "https"` + `osBase(host)`；`osHost` 解析 endpoint（`normalizeHost` 去协议/路径、IP 形式不拼 bucket 子域→天然 path-style、`ossHostPattern` 按 kind 推默认域名）。

## 七、与计划的偏差（均为实现期必要调整）

1. `signer` 接口比计划多一个 `resource` 形参、并把「payloadHash」改为「payload 原字节」——签名需要 canonical 路径，正文摘要两家算法不同，交给各自 signer 从原字节推导（理由见 §八）。
2. 计划里「endpoint 做包级变量便于测试引流」改为 `objectStoreScheme` 包级变量 + endpoint 填假服务 `IP:端口`：IP 形式天然走 path-style，请求 path 恰等于签名资源 `/<bucket>/<key>`，省掉 DNS 与 TLS。
3. 计划的 `osFactory/initObjectStore` 双层包装合并为单个 `newObjectStoreAcct`，注册文件只负责取配置与补默认值。
4. `Upload` 本批整段缓冲单 PUT（与存量三家一致），分块续传留 PR-B；`List` 单页 1000 条不翻页，超大目录会截断（PR-B）。
5. `Quota` 按计划只对 OSS 生效，COS/S3 返回 `{0,0}`。
6. 绑定生成命令去掉了 `-clean=true`（事故见 §八「绑定重生成」条目）。

## 八、验证到哪一层

- **单测**：新增 `tools/clouddrive/objectstore_test.go`（767 行，内存 KV 假对象存储）15 个用例全绿，覆盖计划 §6 的 7 项：两种 signer 的 Authorization 形态（OSS base64 可解且为 20 字节摘要 / SigV4 credential+scope+64 位 hex）、List 的 CommonPrefixes/Contents 归类与 `encoding-type=utf-8` 还原（含带空格与 `+` 的文件名）、Upload→Open 字节一致、Mkdir/Rename/Move/Delete 的 copy+delete 调用序与 copy-source 头形态、presign 两套参数与 86400 有效期、`AddObjectStore` 落盘文件不含明文 AK/SK 且 `AccountView` 无密文、registry 三 kind 注册与 `New` 分发、`osHost` 推导、region 从 endpoint 反解、200+XML Error 必须透出。`go test ./tools/clouddrive/ -count=1` exit=0（~1.9s）。
- **修掉一个真机必踩的缺陷**：`do()` 原先把**正文 MD5** 当作 `payloadHash` 传给 signer，而 `s3Signer` 又对它再做一次 SHA256 当 `x-amz-content-sha256`——即「SHA256(MD5(body))」，真实 COS/S3 会以 `SignatureDoesNotMatch` 拒掉所有**带正文**的请求（GET/DELETE/HEAD 不受影响，故 httptest 层完全发现不了）。现改为传正文原字节、两家各自取所需摘要，并补 `TestUploadBodyHashes` 断言 `x-amz-content-sha256 == sha256Hex(body)`、`Content-MD5 == base64(md5(body))` 作回归锁。
- **Go 三道**：`gofmt -l tools/clouddrive` 无输出；`go vet ./tools/clouddrive/ ./services/app/` exit=0（全仓 `go vet ./tools/... ./services/...` 只剩 `tools/screenshot` 两处既有 `unsafe.Pointer` 告警，与本次无关）；`go test ./tools/clouddrive/` exit=0。
- **三态构建 exit=0**（改完签名后重跑，并用 PE `MZ` / ELF 文件头核验确实是目标平台产物）：`go build -o bin/_chk_win.exe .`（Windows 桌面）、`GOOS=windows go build -tags server`（Windows 面板）、`GOOS=linux CGO_ENABLED=0 go build -tags server`（Linux 面板，零 cgo）。产物已删除。
- **绑定重生成**：`wails3 generate bindings -ts -i`（CLI v3.0.0-beta.12，与 go.mod 一致）→ 3 Services / 691 Methods / 243 Models，核实 `Tools/services/app/app.ts` 含 `CloudAddObjectStore`、`Tools/tools/clouddrive/models.ts` 的 `AccountView` 含 `bucket/endpoint/region`。真实内容差异只有 4 个绑定文件（`services/app/app.ts`、`services/config/models.ts`、`tools/clouddrive/models.ts`、`tools/ftp/models.ts`），其余为行尾 EOL churn。
  - ⚠️ 事故记录：按计划原文执行 `-clean=true` 时，本次分析返回「0 Services, 0 Methods」而 `-clean` **已先清空** `frontend/bindings`（只剩 2 个文件）。用 `git checkout -- frontend/bindings` 恢复 75 个文件后改用不带 `-clean` 的调用成功。后续生成绑定优先不加 `-clean`，或先确认工作区干净。
- **前端**：`npx vue-tsc --noEmit` exit=0；`npx vite build` exit=0（仅既有 chunk>500kB 告警）。
- **未验证（须真机确认）**：① 真实 OSS/COS/S3 是否接受本签名（尤其 `?stat`、copy 的 `metadata-directive`、COS region 写法）；② 虚拟主机式 bucket 子域解析；③ 跨盘转存 OSS⇄百度/阿里 的端到端；④ GUI 上面三态分流与账号副标题；⑤ 中文/特殊字符 key 在真实服务上的编码往返。均受限于本环境无真实凭证、无图形界面。
