## 诉求

门户上传页一个 2.5 GB 的 ota zip 只有「上传中…」纯文本——无进度、断了整包重来。要加上传任务、进度（复用下载那套进度组件做公用）、切片、队列。

已锁定参数（本窗口用户拍板）：交付 P1+P2 一起；8 MiB 阈值 / 4 MiB 分片；发送侧并发 2、服务端 maxSessions 8（超 init 返 429）、会话 TTL 24h。

## 改动（按落点）

### P1 服务端（`tools/lanshare`，零 cgo 跨平台，无 build tag）

- **新增 `upload_session.go`（切片接收会话协议）**：
  - `sid = sha1(name|size|mtime)` 前 16 位十六进制，**服务端权威生成**——客户端传不进 sid，挡路径穿越；同文件重传命中同 sid → 回 `have`（已收分片下标）续传。
  - 落盘 `appdirs.Data("lanshare")/uploads/<sid>/{data.part(稀疏), meta.json}`；`meta.json` 原子写（先 `.tmp` 再 rename）。磁盘为唯一真源，内存 `liveSessions` 只是加速——服务重启后 `findLiveSession` 仍从 meta 恢复续传。
  - 路由处理：`handleUploadInit`（校验名/黑名单/大小 → 新建或复用会话，新会话才占名额并先 `gcExpiredSessions` 腾位，满返 429）、`handleUploadPart`（`MaxBytesReader(chunkSize+1)` → 校验长度 == 期望 → `WriteAt(idx*chunkSize)` → 标记 done → 按秒节流发 running）、`handleUploadComplete`（分片齐校验 → `uniqueCreate` 落收件箱 → `io.CopyN` → 删会话目录 → 发 done 100%）、`handleUploadAbort`（删目录 → 发 canceled）、`handleUploadSessionGet`（回 have/received/percent）。
  - 常量：`uploadChunkSize=4MiB`、`maxSessions=8`、`sessionTTL=24h`；单文件仍 `maxUploadBytes` 2 GiB。
  - 包级 `ListUploadSessions()` / `AbortUpload(sid)`：扫 uploads 目录回会话快照（Name/Size/Received/Percent/UpdatedAt）/强踢，服务停着也能列/删残留。
- **`pack.go` `Progress` 扩字段**：加 `ID string json:"id"`（=sid）、`Status string json:"status"`（queued|running|paused|done|error|canceled），与下载/云盘负载键对齐。
- **`server.go` `handle`**：并入上述 5 个端点 case；**`/upload` 前缀豁免每 IP 限频**（否则 2.5 GB÷4 MiB≈625 分片 PUT 会击穿 120/min 桶），靠 maxSessions + 大小上限 + 单片上限三重护栏兜底。旧 `POST /upload`（小文件/curl 直投）保留不动。
- **`portal.go` `indexHTML` 重写为纯内联切片队列**：发送侧队列 `THRESH=8MiB`、`MAXC=2`；<8 MiB 走旧 FormData 一次性 `/upload`，≥8 MiB 走 init→逐片 `PUT part(file.slice)`→complete。每文件一行手绘进度条 + 百分比 + 速度 + ETA + 暂停（停发后续片）/继续（resumed 标记让循环继续，不重 init）/取消（abort）/重试。无 Vue、无静态资源依赖。因走 `fmt.Sprintf(indexHTML, inbox)` 注入，JS 里字面 `%` 写成 `%%`（`var PCT='%%'`）。

### P3 集成测试（`upload_session_test.go`，httptest 驱动真实 handle 路由）

新增 5 个协议级用例：乱序分片拼回 + 末片不满 + 齐片前 complete 应 400、重传命中同 sid 回 `have` 续传、会话数超 `maxSessions` init 返 429、超 TTL 会话被 GC 清盘、abort 删目录 + 发 `canceled` 事件，并断言 `done` 事件携带 `ID=sid`/`Status`。

**这些测试抓到两处此前从未被触发的真 bug（均在 `handleUploadInit`/`handleUploadComplete`，Linux 语义下会潜伏、Windows 下必现）：**
- **init 的 GC 顺序倒置**：原代码 `gcExpiredSessions()` 跑在 `sess.save()` 之前，而新建会话目录此刻还没有 `meta.json`——GC 的孤儿清理（`RemoveAll` 无 meta 目录）会把**本会话刚建的目录删掉**，于是后续每个分片 `OpenFile` 找不到目录返 500、名额也永远数不满（meta 缺失不计入存活）。**整个切片上传 happy path 当时是全坏的**。修法：新会话先 `save()` meta（带新鲜 updatedAt）再 `gcExpiredSessions()`，超上限则回滚本会话目录并 429。
- **complete 删目录早于关句柄**：`data.part` 由 `defer src.Close()` 到函数返回才关，但 `os.RemoveAll(sess.dir)` 在其之前执行——Windows 不允许删仍被占用的文件，会话目录（`data.part`+`meta.json`）残留不删（Linux 会成功，故此前只编译/无浏览器验证没暴露）。修法：成功路径 `RemoveAll` 前显式 `_ = src.Close()`（defer 再关一次为无害 no-op）。
